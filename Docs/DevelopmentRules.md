# Правила разработки PanelKomplekt

Правила обязательны всегда. Они могут дополняться и меняться по ходу работы; при изменении правится этот файл.
Как настроить компьютер и выполнять типовые действия — в [DeveloperGuide.md](DeveloperGuide.md).

## 1. Коммиты
Все коммиты пишутся **только на русском**. Для каждого изменённого файла указывается:
```
сделано в файле <имя файла>, <что именно сделано>, <для чего>, <какие есть риски или проблемные места>
```
Если в коммите несколько файлов, каждому файлу отводится своя строка (пункт) в теле коммита.
Первая строка коммита — краткий итог на русском (например: `C101: команда вывода ID выбранного элемента`).
Строки авторства на английском (`Co-Authored-By` и т.п.) не добавляются.
Push в удалённый репозиторий — только по отдельному решению владельца проекта, после проверки коммитов.

Пример:
```
C101: команда вывода ID выбранного элемента

- сделано в файле C101_ShowElementId.cs, добавлена команда выбора элемента и вывода его ID, для проверки работы плагина и ленты, риск: для элемента внутри блока выводится ID блока
- сделано в файле CommandCatalog.cs, команда C101 добавлена в каталог, чтобы кнопка появилась на ленте, рисков нет
```

## 2. Расширяемость
Проект рассчитан на множество команд, которые будут дополняться и совершенствоваться.
Общий код (запуск команд, лента, работа с чертежом) выносится в `Core/` и `Ribbon/`, а не копируется между командами.

## 3. Комментарии
XML-комментарии `/// <summary>` обязательны для всех классов и публичных членов, комментарии в коде — там, где логика неочевидна. Всё **на русском**.

## 4. Рабочая папка
- Работа ведётся только в `C:\Users\bogatyrev\source\repos\PanelKomplekt`.
- Файлы из других папок используются только с явного согласия владельца проекта.
- Файлы и папки, путь к которым дан владельцем проекта (вне проекта), — **только для чтения**.

## 5. Именование
- Имена файлов и папок — **только на английском**.
- Команды: `C<номер>_<Название>`, например `C101_ShowElementId`.
  - Каждая команда лежит в своей папке `Commands/C<номер>_<Название>/`.
  - В папке: код `C<номер>_<Название>.cs` и описание `C<номер>_<Название>.md` (шаблон: `Docs/CommandTemplate.md`).
  - Имя в AutoCAD: `PK_C<номер>_<НАЗВАНИЕ>` (префикс `PK_` исключает совпадения с командами других программ).
  - Класс команды лежит в пространстве имён `PanelKomplekt.Commands` (не по имени папки: иначе имя класса совпадёт с именем пространства имён).
- Остальные файлы: по назначению, без номера — `App`, `CommandRunner`, `RibbonBuilder`, `DataCollection` и т.п.
- Нумерация — по сотням, каждая сотня отведена разделу функционала:
  - `C100`–`C199` — служебные и тестовые команды;
  - `C200`–`C299` — раскладка панелей;
  - `C300`–`C399` — спецификации;
  - следующие сотни — новые разделы, закрепляются здесь по мере появления.

## 6. Документация проекта
Документация пишется в Markdown (`.md`), чтобы GitHub показывал её с таблицами и схемами.
- `Docs/ProjectStructure.md` — структура проекта и список команд. Обновляется в том же коммите, где меняется структура.
- `Docs/UserGuide.md` — руководство пользователя. Обновляется при добавлении или изменении команды.
- `CHANGELOG.md` — журнал изменений простым языком. Обновляется в каждой ветке перед слиянием.
- `Docs/DeveloperGuide.md`, `Docs/Glossary.md` — при изменении порядка работы и появлении новых терминов.

## 7. Ветки и слияние
- Основная ветка: `master`.
- Для каждой команды — отдельная локальная ветка `feature/C<номер>_<Название>`; для изменений, не относящихся к командам, — `feature/<Название>`.
- После тестов и **утверждения владельцем проекта** ветка сливается в `master` командой `git merge --no-ff`:
  - rebase и squash не используются: все коммиты ветки (например, все 10) сохраняются в истории `master`;
  - создаётся отдельный коммит слияния.
- Сообщение коммита слияния (на русском): что именно сливалось (ветка, команда, список изменений) и как это повлияло на проект в целом.

## 8. Новая команда — порядок действий
1. `git switch master` → `git switch -c feature/C<номер>_<Название>`.
2. `tools\New-Command.ps1` — создаёт папку, код и описание команды, добавляет её в `CommandCatalog` и в таблицу команд.
3. Реализовать алгоритм, заполнить описание `.md`, дописать дерево в `Docs/ProjectStructure.md`, `Docs/UserGuide.md`, `CHANGELOG.md`.
4. Тесты в AutoCAD → коммиты по правилам п.1 → утверждение → слияние по п.7.

## 9. Выпуск версии
1. Поднять `<Version>` в `PanelKomplekt/PanelKomplekt.csproj` и дописать `CHANGELOG.md`.
2. `tools\Build-Bundle.ps1` → проверить установку архива из `dist\` на своём компьютере.
3. После слияния в `master` и решения владельца проекта — тег `v<версия>` и его push: GitHub создаст релиз с архивом.
